You have a real school waiting. This is not a side project. From day one, treat Shule like a product with real users who depend on it. A Bursar's fee records, a teacher's marks, a parent's access to their child's results — these are not toy data.

The Three Rules of This Build

🧠

Use Claude as a Mentor, Not a Coder

Ask Claude to explain what code does before you use it. If you paste code you don't understand, you've learned nothing. Ask: "Explain this line by line" — every single time.

🚢

Ship Something Real Every Week

At the end of every week, you must have a page or feature a real user could click. No invisible week-long "setup" sprints. Build visible things.

🔐

Security is Not Optional

RLS policies must be written before a page goes live. Finance data must never be visible to teachers. Test this early and test it often.

Authentication & Role System
This is the most critical phase. Get auth and roles wrong, and the entire system is insecure. Build this before any feature.
⏱ 3–4 Days
🚨

Never trust the frontend alone. Every role restriction you build in React (hiding buttons, blocking routes) must ALSO be enforced by Supabase Row Level Security policies. A teacher who knows the URL /fees/ledger must hit a database-level wall, not just be redirected by React.

How Shule Auth Works

Supabase handles authentication (email + password). But we need to store each user's role. We do this by adding a role column to the staff table and using a JWT custom claim to pass it through.

1

Create User in Supabase Auth

When the Secretary registers a teacher, two things happen: (1) Create a Supabase Auth user with email + temporary password, (2) Insert a row in the staff table with auth_user_id linking to the auth user. The Secretary sets the role during registration.

2

Inject Role into JWT via Database Function

In Supabase SQL Editor, create this function (runs when any user logs in):

-- This function adds the user's role to their login token
CREATE OR REPLACE FUNCTION public.custom_access_token_hook(event jsonb)
RETURNS jsonb LANGUAGE plpgsql AS $$
DECLARE
  user_role text;
  user_school_id uuid;
BEGIN
  SELECT s.role, s.school_id INTO user_role, user_school_id
  FROM public.staff s
  WHERE s.auth_user_id = (event->>'user_id')::uuid;
  
  IF user_role IS NOT NULL THEN
    event := jsonb_set(event, '{claims,user_role}', to_jsonb(user_role));
    event := jsonb_set(event, '{claims,school_id}', to_jsonb(user_school_id));
  END IF;
  
  RETURN event;
END;
$$;

Then in Supabase Dashboard → Authentication → Hooks → add this as a "Custom Access Token" hook.

3

Build the AuthContext in React

Create src/store/AuthContext.tsx. This makes the current user's role available everywhere in your app:

import { createContext, useContext, useEffect, useState } from 'react'
import { supabase } from '../lib/supabase'

type UserRole = 'principal' | 'deputy' | 'dos' | 'secretary' | 
  'bursar' | 'class_teacher' | 'teacher' | 'student' | 'parent'

type AuthUser = {
  id: string
  email: string
  role: UserRole
  schoolId: string
  name: string
}

const AuthContext = createContext<{ user: AuthUser | null; loading: boolean }>(
  { user: null, loading: true }
)

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null)
  const [loading, setLoading] = useState(true)

  useEffect(() => {
    supabase.auth.getSession().then(({ data: { session } }) => {
      if (session) {
        // Extract role from JWT custom claims
        const claims = session.user.app_metadata
        setUser({
          id: session.user.id,
          email: session.user.email!,
          role: claims.user_role,
          schoolId: claims.school_id,
          name: claims.full_name,
        })
      }
      setLoading(false)
    })

    const { data: { subscription } } = supabase.auth.onAuthStateChange(
      (_, session) => {
        if (session) {
          const claims = session.user.app_metadata
          setUser({ id: session.user.id, email: session.user.email!, 
            role: claims.user_role, schoolId: claims.school_id, name: claims.full_name })
        } else { setUser(null) }
      }
    )

    return () => subscription.unsubscribe()
  }, [])

  return <AuthContext.Provider value={{ user, loading }}>{children}</AuthContext.Provider>
}

export const useAuth = () => useContext(AuthContext)

Build the Route Guard

This component redirects users to the right dashboard and blocks unauthorized routes:

// src/components/layout/ProtectedRoute.tsx
export function ProtectedRoute({ allowedRoles, children }) {
  const { user, loading } = useAuth()
  
  if (loading) return <LoadingSpinner />
  if (!user) return <Navigate to="/login" />
  if (!allowedRoles.includes(user.role)) {
    return <AccessDenied />  // HARD BLOCK — not redirect
  }
  
  return children
}

// Usage:
<Route path="/fees/*" element={
  <ProtectedRoute allowedRoles={['principal', 'bursar']}>
    <FeeRoutes />
  </ProtectedRoute>
} />

RLS Policies — The Security Layer

Enable RLS on every table, then add policies. Here are the most critical ones:

-- Enable RLS on students table
ALTER TABLE students ENABLE ROW LEVEL SECURITY;

-- Helper function to get role from JWT
CREATE OR REPLACE FUNCTION auth.user_role()
RETURNS TEXT AS $$
  SELECT coalesce(current_setting('request.jwt.claims', true)::json->>'user_role', '')
$$ LANGUAGE sql STABLE;

CREATE OR REPLACE FUNCTION auth.user_school_id()
RETURNS UUID AS $$
  SELECT (current_setting('request.jwt.claims', true)::json->>'school_id')::uuid
$$ LANGUAGE sql STABLE;

-- STUDENTS: Teachers cannot INSERT or UPDATE
CREATE POLICY "secretary_principal_can_insert_students"
ON students FOR INSERT
TO authenticated
WITH CHECK (
  school_id = auth.user_school_id()
  AND auth.user_role() IN ('secretary', 'principal')
);

CREATE POLICY "all_staff_can_view_students_basic"
ON students FOR SELECT
TO authenticated
USING (school_id = auth.user_school_id());

-- FEE_PAYMENTS: Only Bursar and Principal can read
ALTER TABLE fee_payments ENABLE ROW LEVEL SECURITY;

CREATE POLICY "bursar_principal_only_fee_payments"
ON fee_payments FOR ALL
TO authenticated
USING (
  school_id = auth.user_school_id()
  AND auth.user_role() IN ('bursar', 'principal')
);

-- EXAM_RESULTS: Teachers only see their own
CREATE POLICY "teacher_sees_own_results"
ON exam_results FOR SELECT
TO authenticated
USING (
  school_id = auth.user_school_id()
  AND (
    auth.user_role() IN ('principal', 'dos', 'secretary')
    OR teacher_id = auth.uid()
  )
);

The Module Build Pattern

For every feature you build, follow this exact sequence:

1

Write the TypeScript Types First

In src/types/app.ts, define what the data looks like. This prevents bugs later.

export type Student = {
  id: string
  schoolId: string
  admissionNumber: string
  firstName: string
  lastName: string
  classId: string | null
  streamId: string | null
  gender: 'male' | 'female'
  status: 'active' | 'suspended' | 'expelled'
}
2

Write the Data Hook

Create a custom hook in src/hooks/ that handles fetching and caching:

// src/hooks/useStudents.ts
export function useStudents(classId?: string) {
  return useQuery({
    queryKey: ['students', classId],
    queryFn: async () => {
      let query = supabase
        .from('students')
        .select('id, admission_number, first_name, last_name, class_id, stream_id, status')
        .order('first_name')
      
      if (classId) query = query.eq('class_id', classId)
      
      const { data, error } = await query
      if (error) throw error
      return data
    }
  })
}
3

Build the UI Component

Use the hook in your page component. Keep pages thin — they just connect data to UI:

export function StudentsPage() {
  const { data: students, isLoading } = useStudents()
  
  if (isLoading) return <Spinner />
  
  return (
    <div>
      <PageHeader title="Students" action={<RegisterStudentButton />} />
      <StudentTable students={students ?? []} />
    </div>
  )
}

Set Up IndexedDB with Dexie

Create src/lib/db.ts for offline data storage:

import Dexie from 'dexie'

class ShuleDatabase extends Dexie {
  students!: Dexie.Table
  staff!: Dexie.Table
  syncQueue!: Dexie.Table

  constructor() {
    super('shule')
    this.version(1).stores({
      students: 'id, schoolId, admissionNumber, classId',
      staff: 'id, schoolId, role',
      syncQueue: '++id, tableName, actionType, status, createdAt',
    })
  }
}

export const db = new ShuleDatabase()

// Queue a write for when network returns
export async function queueSync(tableName: string, action: string, payload: any) {
  await db.syncQueue.add({
    tableName,
    actionType: action,
    payload,
    status: 'pending',
    createdAt: new Date()
  })
}

The Offline Banner

Show a banner when the local server is unreachable:

export function OfflineBanner() {
  const [isOnline, setIsOnline] = useState(navigator.onLine)
  
  useEffect(() => {
    window.addEventListener('online', () => setIsOnline(true))
    window.addEventListener('offline', () => setIsOnline(false))
  }, [])
  
  if (isOnline) return null
  
  return (
    <div className="fixed top-0 inset-x-0 bg-amber-500 text-white text-sm text-center py-2">
      ⚠️ You are offline — changes saved locally and will sync when connection returns
    </div>
  )
}

Physical School Installation
This is where the software meets the physical world. Install Shule on a school's local server, configure their WiFi network, and set up all staff devices. Plan for a full day on-site.
⏱ 1–2 Days on site
⚠️

Bring everything with you. Schools often have slow or no internet during your visit. Arrive with: a USB drive containing the full Shule build + Docker images, a network switch if needed, printed IP address configuration sheets, and printed login credentials for all staff.

What You Need Before Going to School

  • A dedicated PC or server to act as the Shule server (min: 8GB RAM, 256GB SSD, i5 or better)
  • Ubuntu Server 22.04 LTS installed on the server machine (download ISO in advance)
  • Docker and Docker Compose installed
  • The Shule production build (npm run build) on a USB drive
  • Supabase self-hosted Docker images downloaded
  • A WiFi router or access to the school's existing network
  • Credentials list: all staff email + temporary passwords (printed, sealed envelope)
  • School data preloaded: students, staff, classes, fee structure

Installation Steps on School Day

1

Set Up the Server Machine

Install Ubuntu Server 22.04. Assign a static local IP address (e.g. 192.168.1.100). This address must never change — all staff devices will bookmark this IP.

# Install Docker
sudo apt update && sudo apt upgrade -y
sudo apt install docker.io docker-compose -y
sudo systemctl enable docker

# Create the shule directory
mkdir /opt/shule && cd /opt/shule
2

Deploy Supabase Self-Hosted

# Clone Supabase self-hosted starter
git clone https://github.com/supabase/supabase
cd supabase/docker
cp .env.example .env

# Edit .env — set your passwords (save these securely!)
nano .env

# Start Supabase
docker compose up -d

# Check it's running (Studio at http://192.168.1.100:3000)
docker compose ps
3

Deploy the Shule Frontend

Copy the dist/ folder from your USB drive. Serve it with Nginx:

sudo apt install nginx -y

# Copy built frontend
sudo cp -r /path/to/usb/dist /var/www/shule

# Configure Nginx
sudo nano /etc/nginx/sites-available/shule
server {
    listen 80;
    server_name 192.168.1.100;
    root /var/www/shule;
    index index.html;
    
    # For React Router — serve index.html for all routes
    location / {
        try_files $uri $uri/ /index.html;
    }
    
    # API proxy to local Supabase
    location /api/ {
        proxy_pass http://localhost:8000/;
    }
}
sudo ln -s /etc/nginx/sites-available/shule /etc/nginx/sites-enabled/
sudo systemctl restart nginx
4

Connect Staff Devices to the Network

Every staff laptop, tablet, or phone must be on the same WiFi network as the server. On each device:

  • Open Chrome or Firefox
  • Navigate to http://192.168.1.100
  • Shule loads — click "Install App" in the browser for PWA install
  • Log in with their provided credentials
💡

Create a QR code pointing to http://192.168.1.100. Print and paste it in the staffroom. Staff scan it to open Shule on their phones.

5

Run a Training Session

Spend 2–3 hours with the key staff. Train in this order:

  • IT Admin (30 min) — Settings, user management, password resets
  • Secretary (45 min) — Student registration, import data, generate portal links
  • Bursar (45 min) — Import fees, add payments, send reminders
  • Teachers (30 min) — Exam journal, enter marks, attendance
  • Principal (30 min) — Dashboard, approve report cards, audit log

Server Maintenance Tasks

Daily Automatic Backup

Set up a cron job that backs up the PostgreSQL database to a USB drive every night at midnight:

0 0 * * * pg_dump shule > /mnt/backup/shule_$(date +\%Y\%m\%d).sql

Power Cut Recovery

Configure the server to auto-start Docker and Nginx on boot:

sudo systemctl enable docker
sudo systemctl enable nginx

After a power cut, staff simply reconnect to WiFi — the server will have restarted all services automatically.

MVP Definition & Handoff
What exactly constitutes a working MVP? What must be done before you hand over to the school? This checklist is your exit criteria.
⏱ Ongoing

MVP Exit Criteria

Shule is MVP-ready when ALL of the following are true:

  • All 9 roles can log in and see their correct dashboard with correct sidebar
  • Secretary can register a new student through the 3-step wizard
  • Bursar can import fee statements from Excel and add new payments
  • Teacher can create an exam journal entry, enter marks, and view charts
  • Report cards can be generated as PDF in CBC format with correct grade formula
  • Principal can approve and release report cards
  • Parent portal shows results, fees, attendance (read-only)
  • Finance data is completely invisible to Teacher, Deputy, DoS roles (tested)
  • RLS policies block unauthorized database access (tested with Supabase inspector)
  • App works offline (IndexedDB) and syncs on reconnect
  • App is installable as PWA on Chrome (Android) and Safari (iOS)
  • All lists are virtualised (no more than 50 DOM rows)
  • Page load on local LAN is under 2 seconds
🎉

When these are all checked, you have a real product. Not perfect — real. A school Bursar can use the fee ledger. A teacher can mark an exam. A parent can see their child's results. That is enough to start charging for the product.
